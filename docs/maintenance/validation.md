# 验证与快速反馈

## 日常 quick 与完整 full

- `pnpm check` / `pnpm check:quick`：日常快速反馈。基于最近验证收据、当前文件指纹及工作区依赖图选择影响包；源代码变化传递到消费者。先零警告 lint，再清理/构建影响包、类型检查、脚本快速回归和包快速测试。quick 固定一个测试 worker；lint、build、typecheck 与测试均通过同一 context 的原生 Job 执行和取消。
- `pnpm check:full`：原完整套件，所有原用例、断言、coverage 和平台跳过保留。默认共享最多两个真实 worker。只有该完整入口成功、输入未漂移且产物/真实 tarball 摘要有效，才写入 `validation.kind=full` 的收据。
- `pnpm check:serial`：同一完整套件的单 worker 诊断入口，也写完整收据；收据仍绑定该次完整环境。`check:full:run` 是内部执行阶段，不独立生成发布收据。

quick 复用 `selectCheckMode` 的传递影响选择。脚本快速回归按 `scripts/tests/quick-*.test.mjs` 约定发现；改动的独立脚本测试也运行。包默认运行其全部测试，可在本包 `package.verify.json` 声明明确 `quickTests` 列表；release-vercel 的快速集合为 config、git、retirement-cli 三个文件，其余真实发布/恢复集成验收留在 full。修改未入选集成测试、共享 helper、清单/配置、检查工具链、删除输入、未知路径、全部包受影响、环境或依赖产物不能核实时，quick 以 `FULL_CHECK_REQUIRED` 拒绝，不自动缩小范围或暗中启动长全量。冷缓存同样要求先运行 full。选中拥有 `test-process-scope.mjs` 约定适配器的监督运行时包时，也要求 full，避免 quick 构建期间替换其监督实现。

quick 输出精确包/脚本/测试文件及 NOT RUN 清单；未运行的完整发布/恢复、tarball 消费者和 coverage 不报告通过。它不写成功收据、不发布局部覆盖报告。并发设置可仅为 quick 的影响选择使用独立环境摘要，full 发布准入仍核对原完整环境摘要（含 worker 设置）、所有输入、dist 和真实 tarball 字节。

所有 npm 发布命令先显式 full；`publishIfNeeded` 在调用、每次打包及 publish 前独立核验 full 收据。旧收据、quick、增量结果、输入/环境/产物变化或缺失均不能授权发布。main 自动 Changesets 发布流程、首次发布 registry 门禁及手动 CI 触发策略保持不变；CI 的验证命令显式使用 `pnpm check:full`。

## 原有内部增量验证

以下记录 `node scripts/check-runner.mjs` 无参数的兼容自动入口；它与日常 quick 的选择共用已有机制。内部增量验证产生的普通收据不带 full 标记，不能满足发布门禁。日常入口不会把这些增量路径冒充完整验收。

兼容自动入口仍按下列旧规则复用已验证输入；它不是 pnpm 日常 quick 的实现。

无参数 runner 使用工作区文件指纹及已验证的构建产物、真实包哈希选择检查范围：

- 指纹完全一致且构建产物、真实包仍匹配时，复用上次通过的结果。
- 仅 Markdown 文档或 Changeset 变化时，复核已验证产物与包哈希并运行零警告 lint。
- 包内 `src/`、`tests/` 或 README 变化时，按工作区依赖图确定受影响包，源码变化另纳入传递下游包。受影响包是全仓的真子集时，单包与包组使用同一流程：先运行零警告 lint，清理目标包旧构建并按依赖顺序重建一次，完整执行真实包、浏览器边界与消费者验证，再按目标包顺序完成类型检查，最后运行全仓脚本测试和选中包覆盖率。Markdown 本地链接检查也重新运行。同次文档和 Changeset 修改不扩大到全仓。
- 仅 `scripts/tests/` 内的脚本测试或夹具、`scripts/ab-eval.mjs` 与 `scripts/ab-eval/` 内的评估工具，或包目录 `evaluation/` 下未列入该包 `files` 的 `.mjs` 工具变化时，运行全仓零警告 lint 与全部脚本测试；后一种复用要求包清单的 `files` 为明确路径列表，不接受通配写法。写入新收据前再次核对输入指纹、所有构建产物和真实包哈希。构建、打包及检查调度脚本等其他脚本修改仍触发完整检查。
- 清单、检查调度脚本、环境、文件删除或全仓包受影响时触发完整检查。缓存缺失或未受影响产物不匹配也回到完整检查。

文档模式与脚本测试模式都会重新检查 Markdown 本地链接。所有复用路径在文档及产物检查结束后再次确认输入未变化；未重新验证的产物沿用原收据哈希，目标包只更新本次验证过的产物哈希。上述复用只适用于相同输入的已通过结果。未完成、失败或输入变化都不能记作通过。修改中文内容后还须检查乱码和可读性。

完整检查由 `scripts/check-full.mjs` 调度。1/2槽模式依次完成零警告lint、干净构建及包验证、类型、循环依赖、脚本和覆盖率；4/8槽模式先完成干净构建，在 `onBuilt` 建立唯一共享context，先启动脚本，脚本通过后并行执行整仓lint、“类型→循环依赖”和覆盖率，包验证同时继续打包、浏览器边界、安装和真实消费者检查。类型感知lint只读取已完成的构建，不与dist清理/构建重叠。脚本、覆盖率和消费者始终预约同一总容量；后台错误立即有接收方并停止新测试启动。完整入口须等待包验证、全部检查、取消收尾及context最终审计全部结束，才允许生成成功收据。消费者及测试仍在读取产物时不能重建或清理 `dist`。定向包组沿用原范围与顺序；脚本复用模式仍先完成lint。

阶段顺序不改变构建或打包工具既有的内部并发配置，也不等于整个验收最多只有两个 OS 进程。共享 worker 预算约束独立测试执行；context 关闭审计完成后才能报告完整检查完成或写入定向成功收据。

完整、定向包组和独立测试入口默认共享最多 **2 个测试 worker**；`FORGE_CHECK_TEST_WORKERS` 接受 `1`、`2`、`4`、`8` 四档，不会提高系统资源限制。包的 `package.verify.json` 可声明较低的 `coverageWorkers` 偏好上限，未声明时可使用当前总预算；实际分配取总预算与声明的较小值。完整覆盖率使用单个工作区Vitest实例，所有项目共享同一个真实fork容量池，并保留显式较低的文件并发上限。Vitest同组要求相同上限，包装器据原groupOrder和档位形成有序子组；显式1槽仍串行，未声明的项目不会全部落入Vitest的全局串行组。配置包装保留包的setup、文件选择和覆盖率provider；无法保持的覆盖率门槛或配置会明确拒绝，不静默忽略。报告按真实来源分回各包，不使用额外包池叠加文件池。

Node脚本阶段按每组2槽保守预约，组数不超过总预算的一半；1槽诊断保留单组及既有的短时嵌套例外。文件按稳定顺序分组，各组继续逐文件启动独立Node测试worker，预留的另一槽覆盖真实故障fixture的嵌套worker。首败取消活动兄弟组并等待全部收尾，尚未启动的组停止。消费者入口导入和每个smoke各占1槽，使用同一预算。测试场景必需的Git、应用、原生监督及故障子进程继续保留；串行诊断入口不禁止这些被测子进程。

根context向所有嵌套任务传递同一个`FORGE_CHECK_WORKER_CEILING`，子context缩小本地预约时不复制总容量。共享事件审计同时统计父测试worker、兄弟及嵌套worker；任何时刻的实际峰值超过根上限、所属worker未关闭或租约未归还，均令验收失败。该并发设置同样绑定完整收据，不能复用另一档的发布准入结果。

完整覆盖率通过`vitest-unified-budget-config.mjs`使用一个工作区项目，复用同一转换图和V8覆盖率转换。测试文件glob、源码coverage范围及每文件超时来自各包的实际配置，worker继续独立fork，保留原受控fork继承的仓库cwd；维护的setup只恢复对应包声明的test/hook超时。低于当前总预算的包上限、额外setup、环境、覆盖率门槛或其他不能保持的配置均明确拒绝；可降低总预算，或明确使用保留的多项目诊断适配器。不会因不支持而静默丢弃门禁或回退。

每个脚本文件仍由独立受管CLI提供进程隔离；CLI使用Node官方的`--experimental-test-isolation=none`，避免再产生未受隐藏参数控制的内层测试进程，不把多个文件放进同一进程。Vitest通过公开pool接口使用原有forks worker，保留IPC、文件隔离、setup和覆盖率执行；后台启动显式隐藏控制台并保留日志管道。

Vitest调度编号可能在旧worker退出前复用，因此真实fork槽持有到父侧观察到OS进程`exit`才释放，不能以afterAll、子进程exit回调或“开始收尾”代替。输出排空沿用项目的`teardownTimeout`；失败会停止后续fork、记入Vitest错误状态并令CLI非零退出，随后由原生作用域核实后代关闭，不能仅记录日志后通过。

测试命令先绑定原生作用域身份再授权执行，等待命令及后代关闭后才归还槽。首个失败停止新排队任务，已运行的兄弟完成收尾后才返回；异常作用域即使已强制清空也不能记作成功。每次运行在忽略目录 `.tmp/check-runs/` 保留独立日志、worker事件、进程关闭证明和覆盖率；同包只有一个Vitest实例，不拆分门槛。全部包成功后才暂存各包覆盖率报告及完整清单；复制和汇总写入完成后再替换旧报告，可捕获的替换错误会回滚。发布成功、复制/汇总失败或回滚成功后清理本次暂存和旧备份；回滚失败则保留恢复数据并报告位置，暂存清理失败也令验收失败。该步骤不承诺跨目录原子可见或进程崩溃后的自动恢复。

每个受管命令另建 `.tmp/test-work/r-*`，以 `FORGE_CHECK_JOB_TEMP` 显式提供给使用该约定的夹具；日志目录先保存所属 Job 与目录身份，终态记录是否移除。只有尚未尝试启动，或父侧确认 Job 已空并完成 dispose，才在身份复核后清理该目录。成功、失败、取消和超时沿用同一收尾；关闭未确认、身份改变或清理失败时保留目录及原因。该机制不清扫历史目录，也不覆盖尚未使用该变量的夹具；宿主崩溃后的恢复仍须核实具体归属与真实失效状态。正式日志和覆盖率证据与可回收工作目录分开，当前尚无历史证据自动轮转，不能把 Job 空或测试通过等同于磁盘无累积。

独立运行 `pnpm test:scripts` 或 `pnpm test:coverage` 前须先运行仓库标准构建 `pnpm build`；完整检查自带该构建步骤，不依赖历史 `.tmp` 或手工预置产物。验证监督器按包内 `test-process-scope.mjs` 约定发现，使用现有显式Windows/Linux Provider，不引入无监督回退。

## Windows 短时窗口取证

`owned-nested-git.test.mjs` 的 `windowsHide:false` 负例在本次自有隐藏控制台下运行12次真实Git及显式Provider。宿主在原生创建边界通过 `STARTF_USESHOWWINDOW/SW_HIDE` 隐藏，暂停加入测试自有、关闭即终止的Job后才恢复；异常和超时必须强制收尾并验证Job为空，不依赖诊断入口的外层Job。实际Node只连接显式宿主PID，拒绝父进程保留值；保存并恢复AttachConsole可能改变的三个借用标准句柄，不关闭借用句柄。逐次核验同一隐藏控制台、stdout/stderr管道、SHA输出和原关闭断言，仍完整接受WinEvent观察。该夹具调整经维护者明确批准，保留false参数及真实Git，但不再覆盖原“无控制台的Git(false)新建console/conhost”路径；true分支及其他正常启动点不采用此隔离，也不据此宣称任意外部false启动都不会闪窗。

`packages/process-control-node/test-window-probe.mjs <run-name>` 是包内显式诊断入口，不属于普通测试或公开包 API。入口宿主须通过 Windows 隐藏启动方式创建；复用标准构建、现有 context 与 Job，以一个 worker 预约执行隐藏 pnpm、一次嵌套 lifecycle 和本地 Git 查询。夹具自行生成最小 Git 对象，不下载依赖、不访问凭据或发布服务。工作预算为 5 秒，沿用 10 秒受管收尾期限；首次可见窗口、采集错误或期限耗尽即取消，不自动循环或扩大到全量。

专用 Worker 使用 WinEvent 消息循环，并通过始终隐藏的自检对象验证真实消息投递。进程身份只从本轮已确认的 Job 成员取得，活动实例保持句柄；只有自有句柄的退出信号已触发，才先撤销其新窗口归属资格并释放句柄，避免历史已退出实例持续占用原生查询链。报告保留完整身份历史，已捕获的闪窗不会删除；退休身份的迟到窗口若无法重新确认仍报未确认。PID复用须重新核验Job归属和创建令牌，同一Job已确认的旧令牌重现不得重复累计。控制台事件中的应用 PID 用于关联 conhost 窗口，并区分 HWND 销毁后的新实例。未知窗口只留 PID、HWND、类名和时间等归属元数据，不记录标题或应用内容。10 毫秒 Job 采样不能保证捕获所有短命成员；身份缺失、消息积压、未知可见窗口或事件数量超限均保留为未确认，不能解读成无闪窗。

窗口成员的必要身份为Job归属、PID及固定句柄取得的创建令牌，不读取映像名称或父PID。这两项不参与窗口关联，不能作为额外准入依赖；不以其他API或权限替代受拒元数据读取。列表返回后先固定整批新成员句柄，再逐个验证Job归属和创建令牌，未验证的句柄不发布为成员；失败后仍释放整批已固定句柄。OpenProcess、IsProcessInJob及GetProcessTimes等必要身份步骤失败仍立即停止，保存具体步骤和原生错误码；打开实例失败时另留批量大小、此前已固定数量和查询至失败的耗时。启动链来自本轮命令及阶段记录；缺少进程名称时不猜测具体可执行文件。

收据保存在 `.tmp/windows-flash-investigation/`，包含阶段、窗口、进程身份、Job 关闭和 worker 收尾。`visible-window-captured` 表示已捕获自有可见窗口；`not-reproduced` 只表示该次完整短链路未复现，不能证明所有启动入口都隐藏。夹具失败或超时不能生成未复现结论，更不能替代 `pnpm check:full`、`pnpm check` 或桌面实际观察。

短夹具默认保留 512 条事件及每个 Job 最多 512 个成员实例；完整验收可显式选择最多 32768 条事件和每 Job 32768 个历史实例，仍然有界，超限继续报未确认。历史实例数量包含已退出而仍固定身份的进程，不代表活动 worker 并发；采集额度不扩大测试 worker 并发，也不改变现有测试超时或断言。

历史保护号码默认在打开进程前拒绝。只有维护者显式批准的号码子集可核验本轮复用：每次订阅固定Job创建序号的起点，原生记录必须确实观察到此后成功创建的无名Job、仍对应当前未关闭的注册对象及受控根启动链；具名Job可能只是打开旧对象，不作新建证明，并清除可能残留的同号句柄记录。仅处理该Job实际列出的成员，固定句柄后先确认Job归属，再读取创建令牌，出生时间还须晚于本轮采样器建立且不晚于当前检查；UTC时间相同或回拨不能替代创建序号的先后证明。成功身份按Job注册实例及PID/令牌去重，有界保存核验依据；旧、未来、未知或原生失败仍停止并释放本轮句柄，失败后收尾不再发起pending采样。观察器及启动宿主的硬保护不可覆盖，采样器自身也默认保护当前进程，外部窗口归属检查仍拒绝所有保护号码；旧Job、目录及旧实例不因同号许可获得查询或操作权限。

诊断可能遇到返回成功但 assigned/count 不同的原生成员查询，不能直接认定该差异无害。容量足够时，先固定并验证返回的唯一PID集合，最多用原20毫秒取得一致列表或证明新增实例覆盖；先前列表中消失的成员身份仍保留。常规采样间隔为10毫秒，待确认列表在同次调用最多立即补查一次，不循环等待计数收敛；仍待确认才让出到下一事件循环check阶段，最多保留一个补采样回调。调度判断只读当前pending状态，不复制历史快照；首次闪窗、缺口或关闭会停止后续查询并撤销该回调。窗口事件持续采集，已知成员的首次可见事件立即取消，不等待计数收敛。

新增实例覆盖仅使用同一已注册且未关闭Job的[生命周期累计进程数](https://learn.microsoft.com/en-us/windows/win32/api/winnt/ns-winnt-jobobject_basic_accounting_information)。每次依序读取累计量、PID列表、固定并核验整批新实例、发布成员身份，最后再次读取累计量并重查原20毫秒期限。唯一列表数字一致且前后累计量相同时，建立完整活动集合基线；数字一致但累计量变化时保留旧基线。数字不同仅在有效基线之后的累计新增数等于该Job已确认新实例数、全部持有句柄均已确认且期限未到时，才记录为instance-delta并推进完整性链。确认数只在成员发布成功后增加；累计量对所有先前读数保持单调，不扣除失败关联的额外计数来凑等式。没有基线、重复PID、累计回退、原生或身份失败、容量不足、超过期限或关闭前仍未确认均报采集缺口。这只证明基线之后的新增覆盖，不保证历史所有短命实例均已捕获。

每次计数变化的初始值、最终值、查询次数、最长单次查询耗时、最长查询间隔和结算方式随收据有界保存。增量证明另保留基线出处、累计数、确认数及新增差额；原始不一致数字不改写，不以重读结果覆盖原始证据。

可见非控制台窗口在归属宽限后仍无自有成员关联时，可针对WinEvent明确报告的PID做一次只读补证：首个外层Job仍为原注册实例且未关闭，事件线程与当前HWND/PID/线程一致，固定进程实例创建早于外层Job，固定线程实例创建不晚于事件并属于该进程，查询前后两个实例均存活，且IsProcessInJob对所有当前自有Job均成功返回false。首个Job一旦关闭，句柄值复用不能恢复证明资格。证明按窗口生命周期记录为outsideJobWindows，不采集外部进程映像、父PID、命令行或窗口内容；只证明在本轮Job外，不建立服务代理等跨Job启动的因果保证。控制台、类名读取失败、受保护的历史UNKNOWN/宿主PID、查询失败、退出或身份变化均保留未知。迟到的自有关联与已有证明冲突时仍立即失败；不按类名豁免。该机制要求诊断入口先建立覆盖正常后代启动链的外层Job，并在本地调用参数中保护已知宿主和排除PID。

## 手动 CI 验收

`.github/workflows/ci.yml` 仅接受 `workflow_dispatch`。不添加 push、PR、schedule、`workflow_run`、`workflow_call`、`repository_dispatch` 等自动或间接入口，也不从其他自动化中代为 dispatch CI。默认分支合入此配置后才完成策略切换；仅更新开发分支时，默认分支的旧触发器仍可能运行。

发布前由维护者执行一次完整手动验收：

1. 确认候选提交已推送，工作区干净，并记录 `git rev-parse HEAD` 与 `git ls-remote origin refs/heads/<branch>` 返回的精确 SHA，两者必须一致。
2. 在 GitHub Actions 的 CI 页面选择验收分支并执行 Run workflow，或显式运行 `gh workflow run ci.yml --ref <branch>`。默认分支必须已包含 `workflow_dispatch` 配置。不要自动重试或用占位成功状态替代验收。
3. 使用 `gh run list --workflow ci.yml --branch <branch> --event workflow_dispatch --json databaseId,headSha,event,status,conclusion` 找到本次运行，再用 `gh run view <run-id> --json headSha,event,status,conclusion,jobs` 核对事件、精确 SHA 和结果。必须是候选 SHA，所有矩阵任务均成功，不能接受旧运行、跳过任务或仅有部分平台通过。
4. 保留运行链接和候选 SHA 作为验收证据。Linux Ubuntu 24.04 上的 Node.js 22、24、26，以及 Windows 2025 上的 Node.js 24 均运行冻结依赖安装与`pnpm check:full`，涵盖构建、lint、类型检查、循环依赖、覆盖率、浏览器边界和真实 tarball 消费验证。
5. 候选提交发生任何变化后重新验收并核对新 SHA；合并或发布时再次确认实际交付 SHA 与验收证据一致。

切换前只读核实目标分支的 required status checks、规则集及合并队列。手动运行绑定候选提交；若保护要求其他提交或自动事件的检查，先明确满足方式和所需最小规则调整，再由维护者确认。不得自行降低保护、伪造状态或绕过权限错误；未解决的 required checks 应作为合并阻塞报告，避免永久 pending。

独立的 `.github/workflows/release.yml` 继续沿用 main push 与手动预发布入口，按[发布流程](releases.md)执行；它不会代为启动 CI。手动 CI 策略不取消发布流程自身的 `pnpm check:full`、构建、打包验证与发布门禁，main 更新仍保留原有自动发包契约。
