# 仓库与能力边界

本文是 Foundation Forge 的仓库级能力归属与准入规则。具体 package 的安装、入口、API、示例和限制不在这里重复，统一从 [中文文档入口](../README.md) 进入。

## 分层职责

| 层级 | 所有权 | 依赖方向 |
| --- | --- | --- |
| 公共基础层 | 领域中立、可独立版本化、跨产品复用的 TypeScript contract 与 Provider | 只依赖领域中立第三方基础库或本仓库更底层公开包 |
| 高性能运行时层 | 渲染、Native/WASM、高性能计算和运行时适配 | 可依赖公共基础层，不要求公共基础层理解运行时实现语义 |
| 平台与服务层 | AI、数据、网络服务和平台级编排 | 可依赖公共基础层及明确需要的运行时能力 |
| 产品与业务层 | 房间、匹配、业务流程、UI 和客户语义 | 可组合下层公开能力，领域规则保留在本层 |

依赖必须从拥有领域语境的上层指向中立基础层。Foundation Forge 不引用具体消费者，不反向依赖消费者代码，也不复制消费者配置、术语和业务语义。

## 能力准入规则

一个能力进入 Foundation Forge 前必须同时满足：

1. 至少两个独立消费者已经共享同一问题与稳定 contract。
2. contract 不包含 AI、游戏、房间、业务流程、具体 UI 或客户语义。
3. 能力可以单独安装、测试和版本化，不要求消费者引入无关基础设施。
4. 第三方实现可封装在独立 Provider 中，中立 Core 不暴露实现库类型。
5. 代码及依赖许可证允许以 Apache-2.0 仓库公开分发。

仅因“未来可能复用”不构成准入依据；尚未稳定或只有一个消费者的实现继续由原仓库持有。

## Core、Provider 与集成层规则

- Core 优先保持 runtime-neutral，不为方便调用而隐式引入 Node.js、文件系统或第三方 Provider。
- 平台相关实现使用显式 Provider 或显式子入口；消费者负责选择，不做运行时自动探测和隐式 fallback。
- 对外 contract 使用 Foundation Forge 自有中立类型，不向上泄漏 libp2p、`ws` 或操作系统实现类型。
- 组合包可以依赖更底层原语，但依赖图必须保持有向无环；低层包不得反向依赖组合层。
- 文件系统、进程或网络能力只拥有自身通用机制；产品目录、业务重试、服务编排、日志呈现和恢复策略留在消费者。

## 常见能力归属

- **数据库**：连接、迁移和 ORM 装配保留在拥有数据模型的应用；只有形成多消费者稳定中立 contract 后才评估提取。
- **文件 I/O**：产品目录、权限和文件语义保留在应用；便携路径、完整性、格式转换等领域中立原语可独立提取。
- **渲染与 Native/WASM**：属于高性能运行时层，不进入公共基础层。
- **网络**：中立连接、消息、发现 contract 可以进入公共基础层；具体 transport/Provider 独立封装。
- **房间、Lobby、匹配**：属于产品与业务层，可组合网络 Core，但不得把房间语义下沉。
- **AI service、agent、模型适配**：属于平台与服务层，不进入 Foundation Forge。

## 通用 contract 约束

公开能力优先返回结构化错误、诊断和结果，不生成产品级用户文案。资源上限、平台、Provider、大小写策略或其它会影响安全语义的选择应由 API 明确表达，不根据环境静默猜测。

Foundation Forge 提供的安全检查只对其 contract 声明的范围负责；调用方仍负责凭据、授权、并发控制、业务身份、数据来源和产品策略。不得把“通过基础校验”描述成整个产品流程已经安全。
